Fetches all pairs before a transaction; transactional admin recheck and an advisory lock protect the batch and serialize concurrent syncs. ## Review fix: coordinating sync and manual writes

Manual FX POST and DELETE now acquire the same transaction-scoped PostgreSQL advisory lock as sync, after locking the session user. This coordinates all implemented HTTP FX writers, so a manual create cannot enter between sync's lookup and insert. Each path releases on transaction commit or rollback. Raw SQL writes by external processes do not participate in this application lock; the database unique constraint still prevents duplicates, and a conflicting raw insert can cause a safe 500/rollback.

Added `TestFXSyncCoordinatesDistinctAdminWrites`, which holds the advisory lock in a separate database transaction, starts a sync and manual POST as distinct admins, verifies both are blocked on advisory locks, releases it, and checks the valid create/conflict and created/updated count combinations and final provider rate. It repeats using two different admins issuing syncs, requiring exactly one creation and no updates. Before the fix the new test failed because the manual POST was not waiting. A separate mutation removing the sync lock failed the same test (`expected 1 advisory lock waiters`) and was restored. Cleanup releases the barrier before closing the pool. Focused test passed on real PostgreSQL. Final full suite is running.

A second deterministic sequence queues manual POST first and sync second under the held advisory lock, confirming POST 201, sync `created=0, updated=1`. The sync-first case confirms one creation and manual 409; both scenarios and the distinct-admin sync/sync case pass focused PostgreSQL testing.
