# Task 22 report

The standalone customer-create parser preserves omitted, null and concrete values in individually typed fields. It validates the schema in declaration order, ignores unknown fields, normalizes contact and CC emails, and applies the customer service's withholding defaults and stored-value overlay. No route or database writes were added. The frontend form sends aliases and split CC address lists, and supplies NONE/null/false for disabled withholding.

The focused differential table invokes real Python FastAPI/Pydantic and the customer withholding service. It covers required fields, aliases, omitted/null, booleans, email and CC list validation and de-duplication, currency and Unicode lengths, and withholding defaults, type errors and rate boundaries. Three stored-value cases compare type changes and explicit nulls with Python. A separate table compares malformed and non-object JSON errors with FastAPI. The body-size and numeric-exponent bounds have explicit tests.

Test-first evidence: the differential test failed to compile before the parser existed; the withholding-switch test failed to compile before its normalization function existed. Five deliberately changed guards produced red tests and were restored: body size, exponent bound, name minimum length, CC de-duplication and the withholding upper boundary.

Safety and parity limits: bodies larger than 1 MiB are rejected with a custom `body_too_large` error. Decimal lexemes over 4096 bytes and exponents over 1000 are rejected even where Python may accept them. The existing Go email normalizer is reused and has its own documented approximation of Python's email validator. Decimal spellings accepted by Python beyond the Go decimal regex, and exact canonical Decimal serialization for exponent or leading-zero spellings, are not fully matched. Malformed JSON diagnostics reuse the existing item parser and may differ outside the tested examples. These limitations should be resolved or explicitly accepted before connecting a route. The tests are representative rather than exhaustive for all fields and independent guards.

The focused customer tests passed after implementation. The full suite passed with the requested Python and Postgres environment after the final mixed-invalid-CC ordering fix. No production, provider calls, commits, deployments, or Python modifications were made.

## Review fixes

Withholding rates that persist must be exactly representable in PostgreSQL `NUMERIC(7,4)`; nonzero digits beyond four decimal places and values exceeding its precision are rejected, including rates that would round to 0 or 100. Trailing zeroes are accepted when the value is exact. For a JSON number with a fractional or exponent form that persists, the parser also rejects it when Python's float-to-decimal spelling would change the submitted value. This is a deliberate safety exception: Python parses `99.999999999999999999` as `100.0`, while the quoted string retains the original decimal; both are rejected for an active withholding type because neither can be safely stored at the declared precision. Numeric input such as `2.5`, valid defaults and valid four-place boundaries remain accepted.

CC de-duplication now uses a case-insensitive set, retaining the original spelling and order of the first occurrence. A test covers 6,000 unique addresses followed by 6,000 case variants. Focused tests cover rate precision, trailing-zero equivalence, defaults, boundaries, the real Python numeric/string behavior, and the large CC list. Removing the exact-scale check produced the expected red failures for `0.00001` and `99.99999`; the guard was restored.
The float-decoding guard was also independently mutated off; the Python numeric/string test failed because the numeric input reached the precision guard instead of the required inexact-float rejection. The original guard was restored.

## Discarded-rate follow-up

Withholding normalization now runs before storage precision and float-conversion checks. When the resulting type is `NONE`, Python discards the rate and Go does the same, including for overprecision and numeric JSON values that Python rounds while decoding. Active PPH21/PPH23 rates still must pass both safety checks. Invalid decimal syntax and resource limits still apply before normalization. Real Python differential cases cover explicit, omitted and null NONE types and active withholding. The new test failed before the fix; deliberately restoring a discarded rate caused it to fail again, as did disabling the active-rate scale check. Both mutations were restored.
