# Task 62 — recurring draft notification outbox

The manual recurring trigger inserts one event and its recipient snapshots in the invoice transaction. A repeated cycle returns the existing invoice without a new event. Event IDs and `(invoice_id,user_id)` delivery keys enforce uniqueness. All users present at creation are eligible recipients, matching the existing Python selection. The invoice summary is a snapshot; the worker revalidates each user and reads their current address at every claim and retry. Deleted users are permanently cancelled and their saved addresses cleared. Later invoice deletion does not prevent delivery, so the invoice link can then be stale. The database error path rolls back both invoice and event.

`DeliverRecurringDrafts` is a reusable worker entry point accepting the configured `email.Sender` and application base URL. It atomically claims one due recipient using `FOR UPDATE SKIP LOCKED`, locks the user row through claim commit, and records a two-minute lease. A user update or deletion already in progress therefore completes before that claim decides whether and where to send. It commits the claim before sending, and gives each send a 30-second context deadline. Successful sends are recorded separately; failures store a redacted generic error and retry with exponential backoff capped at one hour. Cancellation leaves the lease for recovery. Delivery is at least once: acceptance followed by a crash or database failure before the success update can resend; SMTP cannot prove exactly-once delivery. The sender implementation must honor context cancellation for the send deadline to bound lease duration. This task does not wire a scheduler. The manual trigger produces a one-draft digest matching Python's manual path; the future recurring scanner must supply explicit batch identity and aggregate its drafts to match Python's multi-draft scan digest.

Fresh databases receive migrations 1 and 2; repeat admission checks exact v2 Goose history and the reviewed PostgreSQL 16 catalog fingerprint. Existing v1 databases and Alembic-managed databases are rejected without upgrade. A safe upgrade requires the previously documented independent-DDL fence; this change does not weaken that rule. Baseline-to-Alembic parity continues to compare only migration 1. No live external send or production database was used.
