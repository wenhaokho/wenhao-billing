# Task 10 report

Implemented `internal/fx` with a generated sqlc query (`queries/fx.sql`, sqlc v1.29.0). `GetRate` uppercases both currencies, short-circuits identical currencies, and selects only the latest direct pair on or before the date; absent rows return `*MissingRateError`. `Convert` returns that rate and a four-place amount, rounding the product first to Python's 28 significant digits, then to four places, both half-even. The FX table is global, without a business ID. There are no provider calls or schema changes.

Tests: `internal/fx/TestFX` uses an isolated pgtestdb database and the actual migrated schema. It covers identity without an applicable row, both currency cases, date cutoff and inclusive boundary, newest rate, separate source and target pair selection, missing and inverse-only rates, zero/negative amounts, positive and negative half-even ties, rate return, four-place exponent, precision rejection, and high-precision cases. Python Decimal generated the expected high-precision values (`123456789012345.6789 * 1.23456789 = 152415787517146.7888` after quantization; `1.23454999999999999999999999999 * 1 = 1.2346`). Initial test-first run failed to compile for the missing API; after implementation it passed.

The product-rounding mutation initially survived; an additional Python-derived boundary case was added and it then failed as intended. Full verification from `backend-go`: `PATH=/tmp/billing-task6-venv/bin:$PATH PGTESTDB_URL=postgres://billing:billing@127.0.0.1:57793/billing_task2_clean?sslmode=disable go test -count=1 ./...` passed all packages, including migrations.

Numeric limits: rates come from PostgreSQL `numeric(19,8)` (at most 11 integer and 8 fractional digits). Four-place quantization rejects results requiring more than 28 coefficient digits (`ErrPrecision`), i.e. absolute rounded amounts of 10^24 or more; this is Python's default precision, not the stricter journal column `numeric(19,4)` limit of 15 integer digits. The caller must enforce the destination column limit. The decimal library uses an int32 exponent and does not model Python's default exponent bounds (Emin -999999, Emax 999999), signals, signed zero, infinities, or NaN; extreme exponents are outside this implementation's supported domain. For ordinary finite database amounts and rates no binary floating point is used.

## Review fix: nonfinite stored rates

PostgreSQL accepts `NaN` in `numeric(19,8)`. `GetRate` now rejects invalid, NaN, infinite, or nil-coefficient pgx numeric values with `*InvalidRateError`, propagated by `Convert`, rather than passing a nil coefficient to the decimal library. This is a deliberate safe-stop difference from Python `Decimal('NaN')`, which can propagate NaN through multiplication and quantization. A real-Postgres test inserts a NaN rate and verifies the typed error through both APIs. The initial test-first build failed for the missing error type; removing the complete guard afterward caused the test to fail with the original nil-pointer panic, and the guard was restored. The full requested `go test -count=1 ./...` command passed again, including migrations.
