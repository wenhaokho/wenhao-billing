# Task 51 — implementation and verification

Implemented `POST /api/v1/invoices` in the Go backend. The handler locks and rechecks the persisted admin inside its transaction; serializes allocation of generated and explicit invoice numbers; computes line, subtotal, discount, withholding and gross-up amounts; inserts the draft and all its lines; and serializes the response before commit. It uses generated sqlc queries and does not post ledger entries. Request bodies are bounded, validation inputs are redacted, responses use no-store, and the route is registered in OpenAPI.

Test-first evidence: the initial real-Postgres test failed with HTTP 405 before implementation and passes after it. Subsequent failing tests drove null handling, negative WHT rate handling, validation detail, coercion and WHT precision corrections.

`TestInvoiceCreateDifferential` uses separate disposable Postgres databases and actual Python FastAPI and Go HTTP handlers. It compares full responses after removing generated IDs and timestamps for MILESTONE, RECURRING and USAGE; multi-line subtotal rounding; discount percent and amount; customer withholding defaults; gross-up in IDR and USD; and selected domain and validation errors. `TestInvoiceCreateDraftPostgres` checks 12 concurrent creates from two admins, unique generated numbers, rollback after the second line fails its foreign key, no journal entries, body and media handling, no-store, demotion, a concurrent demotion holding the admin row lock, and OpenAPI registration.

Independent guard mutations were applied and restored: summing rounded line amounts instead of unrounded products failed the HTTP differential; removing the invoice-number advisory lock caused concurrent creates to fail; removing the admin row lock allowed a draft before demotion committed; committing after the first line caused the rollback snapshot assertion to fail. sqlc generation completed successfully.

Coverage is not exhaustive: the current differential does not yet cover every Pydantic coercion and error detail, all foreign-reference cases, invoice-number collision forms, or every rounding boundary; snapshot coverage focuses on invoices, lines and journal entries rather than every unrelated table. Additional OpenAPI schema detail and boundary verification are still warranted. The required full Go suite passed after the final changes (`go test -count=1 ./...` with the brief’s PATH, PYTHONPATH and PGTESTDB_URL); platform took 229.710s and migrations took 22.114s. The earlier exploratory suite runs were interrupted before completion.

The numbering test also seeded a prefix with `+99`; it failed before the digit-only arbitrary-precision fix and passed afterward. The differential additionally includes a project, item, explicit number and due date.

## Review follow-up: boolean and date normalization

The HTTP differential first reproduced two review findings: JSON numeric `1.0` and `1e0` set withholding gross-up false, producing 100.0000 rather than Python's 102.0400; accepted numeric and midnight-datetime dates returned 422. Normalization now converts validated numeric booleans by value and carries the same validated date into insertion. A further test exposed exponent-form numeric timestamps, which are now normalized consistently before validation and insertion.

The differential sends the original raw JSON to both HTTP servers and covers numeric booleans `1`, `1.0`, `1e0`, `0`, `0.0`, `0e0` with WHT totals; epoch, negative, exponent-form and midnight-with-offset dates; and inexact and invalid dates. It checks invoice and line counts before and after invalid requests in both databases. Focused Postgres tests passed. Restoring the former boolean conversion and independently removing date normalization each made the differential fail; both mutations were restored. sqlc generation passed. The final full suite passed (`go test -count=1 ./...` with the brief’s environment): platform 225.084s and migrations 21.044s.
