# Task 70: recurring scan

The API schedules a recurring scan at the next 02:00 UTC after startup, stops it on shutdown, and honors `SCHEDULER_ENABLED=false`. The injected scan clock uses the process local calendar date, as Python `date.today()` does. The scan selects the current cycle (it does not replay every missed cycle), rechecks pause, end and schedule after locking the template, and uses the manual trigger's shared transaction. An advisory lock keyed with Python's CRC32 job ID serializes scheduler replicas. A scan counts existing due cycles as well as newly created ones.

Each template uses a separate transaction. This is a deliberate safe improvement over Python's all-template transaction: a failure rolls back that template's invoice, lines, event and deliveries while other templates can commit. Failures return a generic error and the scheduler logs a generic failure without provider or SQL details. Existing ambiguous legacy keys prevent generation for the affected template.

Migration 5 attaches a scan batch UUID to newly created draft events. All events created in a run are grouped into a digest per recipient; manual triggers retain individual delivery. Delivery acquires the same advisory lock before claiming work, preventing an active scan's incomplete group from being sent. If a process crashes mid-scan, committed drafts form a deliverable partial batch after the connection releases the lock. Retry uses the same batch membership; delivery remains at least once after provider acceptance. No live provider calls were made. Recipient lookup is current at claim time.

Fresh migrations require exact version 5 metadata and fingerprint. Version 4 and earlier Go databases are rejected, not automatically upgraded; the project has no safe upgrade/adoption path. This is a deployment prerequisite and the scanner must not be enabled against an unupgraded database. An API process starting after 02:00 does not run the missed job until the next scheduled time, matching the in-memory Python scheduler. Ordinary mail-provider at-least-once delivery can duplicate a digest after acceptance and before acknowledgement.

## Review fixes

- API startup now validates PostgreSQL 16, exact current Goose history, absence of Alembic metadata, and the full current schema fingerprint in a read-only repeatable-read transaction before opening its listener or starting workers. It does not apply migrations. Every API pool connection uses the verified public search path; connection-string `options` overrides are rejected. This check is a startup snapshot and does not fence subsequent independent DDL; deployments must prevent concurrent schema changes.
- Template transactions use the same connection that holds the scan advisory lock, including when the pool has one connection. The job lock remains held through the whole scan.
- The scanner snapshots recipient IDs and addresses once per run. Users added during the run receive no incomplete digest; users removed during the run retain coherent queued membership, but the delivery worker rechecks and cancels them. Existing users' current email is checked when claiming delivery.
