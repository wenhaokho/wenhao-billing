# Delivery workers

The Go API runs recurring draft notification deliveries and hosting restore intents in its process. Set `SCHEDULER_ENABLED=false` to disable these workers and scheduled jobs (default: true). Each worker starts after the API listener opens, runs serially, and polls 30 seconds after the previous pass; each pass has a one-minute context deadline. Shutdown cancels the workers and waits for them before closing the database. Provider adapters must respect context cancellation.

Email uses the existing `RESEND_*` or `SMTP_*` settings. Hosting restore uses `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_API_BASE_URL` (default `https://api.cloudflare.com/client/v4`), and `CLOUDFLARE_TIMEOUT_SECONDS` (default 15, maximum 60). Missing credentials leave the corresponding queue untouched and log that the worker is unavailable; invalid configured providers fail startup. Provider failures are logged without their details and are retained for retry. Existing per-item retry delays and two-minute leases remain in effect across replicas. Delivery is at least once: a crash or cancellation after provider acceptance can cause a repeated email or PATCH after lease expiry.

Recurring templates are scanned daily at 02:00 UTC, using the process local date to select the current cycle. A PostgreSQL job lock coordinates replicas; each template is generated in its own transaction and failures are logged without details. Recipients are snapshotted once per scan; new users join future scans and deleted users are cancelled at delivery. New drafts from a scan are grouped into one durable email per recipient; if the scanner crashes, its committed drafts remain one deliverable partial batch. Delivery is at least once. An API restart after the scheduled time does not catch up until the next daily run.

The usage cutoff scan runs daily at 03:00 UTC. No usage meter is wired into the application; the job logs that the meter is unavailable and does not invent usage amounts. Hosting enforcement runs daily at 04:00 UTC when Cloudflare is configured. FX synchronization runs Monday at 05:00 UTC. These jobs use PostgreSQL advisory locks across replicas.

Hosting operations are at least once. A provider can accept a request before the process records its result. Durable leases and target fingerprints preserve uncertainty for retry or manual review; see `migrations/00006_hosting_operation_lease.sql` and `migrations/00007_hosting_claim_state.sql`. Mixed Python and Go writers do not all take the same locks. Do not run them concurrently during cutover without an effective fence.
