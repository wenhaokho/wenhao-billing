# Migration admission

`AdoptAlembic` is deliberately unavailable. PostgreSQL serializable catalog reads do not fence independent schema changes: an independent session can commit DDL after verification while the metadata transaction still commits. The migration advisory lock only coordinates callers that voluntarily acquire it. Table locks alone cannot fence creation of new schema objects. Adoption must remain disabled until an enforceable and verifiable database-wide quiescence mechanism covers all independent DDL throughout inspection and metadata commit; administrative and privileged sessions must be considered. An operator assertion or cooperative advisory lock is not that mechanism. No startup or CLI invokes adoption.

The API checks PostgreSQL version, exact current Goose metadata, absence of Alembic metadata, and the full schema fingerprint in a read-only transaction before opening the listener or starting workers. Pooled connections use the admitted `public` search path; `DATABASE_URL` libpq `options` overrides are rejected. This admission check does not fence independent DDL after startup, so deployments must prevent schema changes while the API is running. The API does not migrate databases at startup.

`MigrateFresh` handles an empty database and rechecks known version 7 metadata and catalog fingerprint. It rejects every database containing Alembic metadata, including databases with manually created canonical goose rows. The deterministic race regression test demonstrates the unsafe historical approach only in a disposable database.

The constants in `runtime.go` and `adopt.go` are PostgreSQL 16 catalog fingerprints, including metadata. To change the baseline or fingerprint query, generate separate disposable databases using the complete Alembic chain and embedded Go baseline, compare business schema and seeds, and compute each fingerprint with the same search path. Compute the adopted signature only on a disposable Alembic database with canonical metadata. Review differences and update constants and regression tests together; never use an unknown or production database as an approval mechanism.

Fresh installs apply baseline 1, recurring outbox 2, hosting restore intent 3, restore lease 4, recurring scan batches 5, hosting operation lease 6, and hosting claim state 7. Repeated startup accepts only exact version 7 metadata and fingerprint; existing versions 1 through 6 are rejected and are not upgraded. A safe versioned upgrade entry point has not been implemented. Future upgrades require exact history and fingerprint verification for every admitted state, a fence against independent DDL during inspection and commit, and regression tests. `MigrateFresh` fails closed on unknown future schema or history. The old direct-goose test did not exercise such an entry point and has been removed.

Integration tests require PostgreSQL 16, `PGTESTDB_URL` pointing to the isolated Alembic reference, and the Python backend's `alembic` executable on PATH. Tests invoke Alembic only against new disposable pgtestdb databases. Activate an environment containing the backend's Python dependencies before running `PGTESTDB_URL=... go test ./...` from `backend-go`.
